# ADR-0021: Prometheus and Grafana on the same VM, reachable only through SSH

- **Status:** Accepted
- **Date:** 2026-09-23

## Context

ADR-0019 gave the API a `/metrics` endpoint. Nothing read it. Metrics nobody
scrapes are a text file the service writes to itself, and three gaps remained:

- **Nothing stored them.** A question answered at 3 am could only be counted
  by someone who happened to run `curl` at 3 am.
- **Nothing watched them.** There were no thresholds, so no failure could
  announce itself.
- **The worker exported nothing at all.** It is a second process, with no HTTP
  server, running every ingestion. The API can answer every request perfectly
  while the worker is dead and every upload rots in `processing` behind a
  spinner the user cannot stop. No HTTP metric of the API would ever say so.

## Options considered

| Option | Pros | Cons |
| --- | --- | --- |
| A hosted service (Grafana Cloud free tier) | Nothing to run or back up; alerts by email out of the box | The metrics of a private service leave the machine, to a third party, for a product whose promise is that documents stay put (ADR-0006). A free tier that changes its terms takes the history with it |
| Prometheus alone, read through its own interface | One container | Its graphs are for debugging a query, not for reading a service. No panel survives the session |
| **Prometheus + Grafana, on the VM, published on `127.0.0.1` only** | The same operational model as the rest of the stack: containers, healthchecks, one compose file. Dashboards and alert rules live in the repository | Two more containers to keep up to date; roughly 900 MB of the 24 GB |

## Decision

- **Two scrape targets, because there are two processes that fail
  independently.** The API serves its own `/metrics`; the worker opens a
  second exporter with `prometheus_client.start_http_server` on port 9100,
  started *before* the embedding model loads so a scrape during start-up finds
  a process that is up and not yet ready, rather than a refused connection
  that looks like a corpse.

- **Ingestion metrics, by outcome.** `knowpilot_ingestions_total{outcome}`
  distinguishes `indexed`, `gone`, and each failure reason the pipeline
  already classified: `unsupported_format` and `no_text_found` are people
  uploading scans - the product working - while `processing_error` is ours.
  A single "failed" counter would have merged the two and pointed at nobody.
  Duration is observed for **every** verdict, including failures: a failure
  that takes nine minutes to arrive is its own problem.

- **Dashboards and the data source are files, not clicks.** Grafana is
  provisioned from `infra/grafana/`, mounted read-only. A Grafana that loses
  its volume comes back identical, and what it shows is reviewable in a pull
  request. The dashboard JSON is generated by `infra/grafana/dashboard.py`,
  because an export from the interface is hundreds of lines of defaults nobody
  reads around the twenty that matter.

- **Seven alert rules, each saying what to do.** An alert whose text is a
  number is a notification. `WorkerDown` waits five minutes rather than two,
  because the worker loads 2.2 GB of weights at start-up and a restart is not
  an incident. `AnswersMostlyRefused` is the rule this product needs and a
  generic stack would never have: refusing is a valid answer, but refusing
  seven times out of ten means retrieval stopped finding anything, and no
  error rate would ever show it.

- **Nothing is published to the internet.** Both containers publish on
  `127.0.0.1` only; reading a dashboard means an SSH tunnel to the server.

- **They sit on their own network, not on `backend`.** A port published from
  an `internal` network is unreachable even from the host - measured, not
  assumed - because such a network has no route for the host to come back in
  on. So `observability` is an ordinary network, and these two containers can
  reach the internet where the worker and the database cannot. The trade-off
  is a small one: by the rules of ADR-0019 these processes hold counts,
  durations and token totals, never the text of a question, a document or an
  answer. What could leak from here is arithmetic.

## Consequences

- An operator can answer "when did this start?" after a weekend. Retention is
  fifteen days: long enough for that, short enough that the disk of one small
  VM never decides it.
- Alerts are **evaluated and visible, but not delivered.** There is no
  Alertmanager, because notifying needs a channel - SMTP, Slack - this
  deployment does not have. Adding one is a service and a secret; it is
  deliberately not done while nobody would read the mail.
- Two more images to follow, both pinned by digest like the rest.
- The worker's healthcheck is still `arq --check`, not its new port: the
  exporter answers whether the process is alive, never whether jobs are
  running.

## Revisit when

- There is a second machine. Scraping across hosts needs service discovery and
  a Prometheus that is not on the same box as what it watches.
- Somebody would actually read an alert - then Alertmanager, and a channel.
- The stack no longer fits in memory alongside the model. Prometheus is the
  first thing to move off the VM, because its data is the least sensitive.
